# Review

A read of this repository against its own claims, done on 2026-10-23 on Windows 11 with
CPython 3.13.5 in a fresh virtual environment. CI runs 3.11. Every number below came from
a run recorded here.

## What it is

A benchmark whose result is that the fashionable method loses. On a synthetic daily
streamflow series with a lag-1 autocorrelation of 0.9987, XGBoost reading twenty
engineered features is beaten by repeating yesterday's value, and fails to beat it on all
five seeds tried. A ridge model on the same features is the only method that improves on
persistence.

The title says "When gradient boosting is the wrong tool", which is the honest framing: it
is a write-up of a negative result, and it is more useful than a leaderboard would have
been.

## What was run, and what passed

Everything CI runs, locally.

| Step | Command | Result |
|---|---|---|
| Lint | `ruff check .` | **All checks passed** |
| Tests | `python -m pytest -q` | **17 passed**, 3.1 s |
| Benchmark | `python src/experiment.py` | **Reproduced exactly from seed 42.** The only change in `results/benchmark.json` was `generated_utc` |
| Artifacts and README | `python scripts/check_repository.py` | **Passed.** 10 artifacts, README agrees with the run to within 0.5%, and 10% for XGBoost |
| Figures | `python scripts/figures/generate_figures.py` | Regenerated **byte-identically** |
| Secret scan | `gitleaks git .` | **No leaks found** |

**The reproducibility here is the real thing.** Refitting six daily methods, three monthly
ones and the whole five-seed repetition produced a `benchmark.json` whose every metric was
byte-identical to the committed file. The single changed line was the timestamp.

**One piece of honesty worth naming.** The README states that XGBoost's exact score is
*not* reproducible across machines, 3.12 here against 3.42 on the CI runner, because the
tree builder's floating point behaviour is platform dependent, and that the ordering is
unaffected because every value seen is well above persistence. `check_repository.py`
therefore compares that one number within 10% and the finding exactly. Declaring the
instrument's precision rather than quoting four digits and hoping is the right way to
publish that, and very few repositories do it.

## What was wrong

### 1. The website cites an evidence file that does not exist

This is the serious one, and it is in `ZQ` rather than here.

`ZQ/src/content/streamflow-world.ts` is generated by `ZQ/tools/gen-streamflow-world.py`,
and both name **`results/forecast_results.json`** as the source of every published metric:

- the module header: "refuses to emit this module unless they match
  `results/forecast_results.json` exactly"
- `export const metricsSource = "results/forecast_results.json"`
- the generator at line 137: `published = json.loads(fetch("results/forecast_results.json"))`

**That file does not exist in this repository.** It did once, up to commit `dba015a`, and
was replaced by `results/benchmark.json` at `a3d8a7a` when the results were restructured.
Two consequences:

1. **A reader following the citation gets a 404.** The site names a file as its evidence
   and the file is not there.
2. **The generator is broken.** It fetches that path over HTTP, so re-running it fails
   rather than producing a stale result, which is the better of the two failure modes but
   still means the module cannot currently be regenerated.

**The published numbers themselves are correct.** They were checked against
`results/benchmark.json` and they match: `day_of_year_mean` at RMSE 90.2985, MAE 89.9354,
R2 and NSE -11.692 are the site's 90.299, 89.935 and -11.692. So this is a broken
citation, not a false number, which is the better half of a bad situation.

Fixed in the `ZQ` repository, where the file lives.

### 2. No diagram at all

Every other featured repository opens with one. This one had four figures and no
architecture or pipeline diagram, in `docs/diagrams/` or anywhere else.

That matters more here than usual, because **the design is the argument**. The result only
means something if the split is chronological and every method is scored on the same rows,
and both of those were prose. A Mermaid flowchart now shows the generator, the 0.9987
autocorrelation, the chronological split, the re-scoring of the baselines onto the same
730 rows, and the four headline scores, with the losing methods in red.

Mermaid rather than an SVG because there was no diagram generator to extend here, and a
text diagram cannot drift out of sync with a palette it does not have. Its numbers are
taken from `results/benchmark.json`, not from the prose.

### 3. No `permissions` block and no `timeout-minutes`

The job only reads the repository, so `contents: read` is the whole requirement. It is the
one workflow in this pass that does real compute, refitting every model and repeating
across five seeds, and it still finishes in about 70 seconds; the cap is 20 minutes.

### 4. Two actions on deprecated Node

`actions/checkout@v4` and `actions/setup-python@v5` target Node 20. Moved to `@v7`.

## What was changed

| Change | Why |
|---|---|
| A Mermaid diagram of the benchmark design | There was no diagram, and the design is the argument |
| Two paragraphs on why the split and the shared rows matter | Both were prose easy to skim past |
| `permissions: contents: read`, `timeout-minutes: 20` | Declared least privilege, and a cap |
| `checkout@v7`, `setup-python@v7` | Clears the Node 20 deprecation |
| This file | The brief asks for it |

## What was not changed, and why

- **`results/benchmark.json`'s timestamp.** Re-running the benchmark rewrites
  `generated_utc` and nothing else. Committing that is churn with no information in it, so
  the file was restored.
- **The four PNG figures have no dark variants**, like most of this portfolio. They carry
  their own white plot background so they stay legible on a dark page. Adding a dark set
  means teaching `generate_figures.py` a second matplotlib style while keeping the light
  PNGs byte-identical for the figure check, which is its own change.
- **The XGBoost tolerance.** 10% looks loose until you read why it is there. It is the
  measured spread of a platform-dependent tree builder, and the finding is compared
  exactly. Correct as it stands.

## Guidance applied

- **[Security hardening for GitHub Actions](https://docs.github.com/en/actions/security-for-github-actions/security-guides/security-hardening-for-github-actions)**:
  the `permissions` block, the timeout, and the action bumps.
- **[GitHub's guidance on READMEs](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-readmes)**:
  a diagram before the results table, so a reader can see what was compared before being
  shown who won.
- **[Google Engineering Practices](https://google.github.io/eng-practices/)**: the dark
  figure variants were declined explicitly as a separate concern.
- **[Conventional Commits](https://www.conventionalcommits.org/)**.
- **OWASP**, via a `gitleaks` scan of the full history, which is clean.
- **PEP 8 via ruff**, which passes over the whole tree.
